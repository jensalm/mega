### The register dialog's picker

- **`projects_root`** in the config, expanded from `~`, absolute or refused; unset means the home directory (`Options.ProjectsRoot`).
- **`Service.Folders(path)`** lists one folder:
  - folders only, sorted, `Git` from a `.git` there, `Registered` from the registry;
  - dot-folders left out, and a link listed only where it resolves to a folder inside the resolved root;
  - read 256 entries at a time, stopping at 2,000 folders or 50,000 entries read (`Stopped`);
  - the way up (`Parent`) offered only while the parent resolves inside the root.
- **Unlisted paths are answers.** Outside the root, missing, unreadable or relative, the reply is 200 with a `Note` and no entries. My first version answered 400, and the suite's run logged a browser console error each time a path outside the root was typed. Since that is ordinary while typing, it is a note now.
- **`validateCheckout`** expands `~`. A path typed in full registers wherever it is.
- **The dialog** (`RegisterProjectDialog`).
  - **The field** starts at the root (`~/Repos/` for Michael, `~/` by default). Its text decides what is listed: up to its last slash is the folder, after it the start of a name, so typing completes and Tab finishes it.
  - **The list** is a listbox driven from the field, with clicks and keys: Down from the field, arrows, Enter or Right in, Left or Backspace up.
  - **The name** follows the folder until edited.
  - **Two fixes the suite found.** Entering an empty folder unmounted the list and lost focus, so Left did nothing; the list now stays mounted with its notes inside. Playwright will not click an `aria-disabled` row, so the registered-folder step clicks with `force`, as a person can.

## A model switch left a Claude conversation spinning

- **What was seen.** Switching an idle Claude conversation from `default` to `fable` left it "running" for about 50 minutes. Interrupt did nothing.
- **Cause.** Claude Code 2.1.327, newer than the tested range (2.1.318 to 2.1.325), answers `set_model` with one live user message, `isReplay: true`, content `<local-command-stdout>Set model to …</local-command-stdout>`, and nothing after it. The adapter mapped it to a `user` event, and the service opens a turn for any user message the runtime reports while none is open (`live.go`, the case for an answer that starts the next turn). No `result` was coming, so the turn never ended. The interrupt went to a CLI with no turn and produced no frame. The capability report has the observation (2026-11-18).
- **Fix.** `mapMessage` maps a top-level user message with `isReplay` to a `native` event, "user/replay", keeping its uuid. Pinned by `TestReplayedUserMessageIsNativeNotAPrompt`. The shim never sets the SDK's `replayUserMessages`, so every `isReplay` on its stream is Claude's own echo. That option is gated in the CLI itself (2.1.327 binary): with it on, every prompt comes back with `isReplay` and its own uuid, and this rule would need revisiting.
- **A conversation already stuck** is cleared by Release (the exit path clears the turn) or a restart. Its log keeps the old `user` event; history is not rewritten.
- **Not done.** No e2e round trip switches the model on an idle runtime. One would have caught this on the version bump.
- **Review.** terminus `914bf8244784`: `clean`, no findings, against a new `projects/mega/` rubric (24 qualities, 10 blocking) in the canon on this machine (`vimes`), whose six blocking locals reconstruct the qualities Michael's reviews cited from the spec. The reviewer was codex, not pi, because pi has no login here. The rubric and its quality files are uncommitted in that canon.
