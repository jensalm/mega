### How Claude marks "No response requested."

- **The mark.** An assistant message whose `message.model` is `<synthetic>`, with `stop_reason` `stop_sequence`, an empty `stop_sequence` and zero usage. Read in the fixture's spike sessions, at every build from 2.1.318 to 2.1.325, from the transcript files and through the shim's `messages` (the SDK's history reader).
- **The other `<synthetic>` message** is an API error ("Login reached its time limit"). It has the same `message` fields, plus top-level `isApiErrorMessage: true` and `error: "authentication_failed"`. The history reader drops both, so read back the two differ only in their text.
- **The rule, first version.** `<synthetic>` with no `error` was bookkeeping. terminus flagged it as blocking: an API error read back after an unclean restart would import as native and hide an unread failure.
- **Michael's decision:** read the flag. The shim's `messages` now reads the session's transcript as well and passes each `<synthetic>` message's `isApiErrorMessage` and `error` on by uuid.
  - **Where it looks:** `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<the checkout's path with every other character a dash>/<session>.jsonl`, or any project folder holding that session.
  - **The rule now.** Bookkeeping is `<synthetic>` with `isApiErrorMessage` present and false and no `error`. Anything else written by no model stays a reply: an API error, live or read back, and a message whose transcript could not be read.
  - **The tests.** A shim test fabricates the transcript, and the Go tests cover live, read back, flag-only and transcript-gone. A real rerun of the interrupt round trip found the flag in the real transcript and passed.
- **When Claude writes it.** Only when the next prompt reaches a run that resumed the session. The first version of the new e2e released and imported at once, and found nothing. The trigger was found with three more real runs:
  - waiting five seconds after the interrupt: nothing written;
  - switching to plan and back after it: nothing written;
  - a start without a prompt: nothing written;
  - a prompt in a resumed run: written.

  A prompt in the same run as the interrupt doesn't write it either (the mode-switch round trip's session).
- **"[Request interrupted by user for tool use]",** the user message Claude writes at the interrupt, is not imported: mega records it live.

### What was built

- **`harness.ConfigRoot` and `harness.Configurer`.** Each adapter declares its roots and include lists, reading `CLAUDE_CONFIG_DIR`, `CODEX_HOME` and `HOME` from the start-up check's operator shell environment.
- **Claude keeps `.claude.json` in `CLAUDE_CONFIG_DIR`** when that is set. That is my understanding of Claude Code, not observed here: neither variable is set in Michael's login shell. mega's trust check still reads `~/.claude.json` regardless, as before.
- **`internal/snapshot`.**
  - **The store.** A content-addressed object store (`objects/<2>/<sha256>`, `0400`), with each snapshot a folder of hard links to it plus `manifest.json` (names, digests, modes, link targets, roots, reason, versions).
  - **Taking one.** A snapshot is staged as `.taking-*` and renamed into place.
  - **Retention.** Ordinary and version snapshots are bounded apart, the newest is never removed, and objects whose link count falls to one are collected.
  - **Comparing.** `Diff` compares a snapshot with the live files at its recorded roots under its recorded lists.
- **The service.** `Options.Snapshots`, nil for the tests and the e2e. The snapshot is taken at the end of the start-up check's background work, and again from the version read before a launch when a version is new.
- **What says so.** The `mega snapshots` and `mega snapshots diff NAME|newest` commands; a snapshot line in `mega version`; `snapshots` on `/api/version`; and a row in the version panel, which now reads `/api/version` again as it opens.
- **The probe's scratch megas set `snapshots.keep: 0`.** They run on Michael's own `HOME`, and a probe's scratch is no place for a copy of his configuration.

### Bounds and cost

- **The defaults are 10 ordinary and 20 at a version change.** They were first 20 and 10. But Claude updates every day or two, so most starts meet a new version, and "kept longer" needs the version pool to be the larger one.
- **A month of daily starts,** simulated with a 342 KB `.claude.json` changing at every start and a Claude update every other day, keeps 24 snapshots (10 ordinary, 14 at a version) in about 9.7 MB on ext4. 8.3 MB of it is the copies of `.claude.json`, the rest directory blocks. The bound caps it near 11 MB.
- **Michael's first real start** will copy 13 files, about 354 KB, measured with `stat` only, nothing read or copied while developing:
  - `~/.claude.json`, 342 KB;
  - `settings.json`, the empty `CLAUDE.md` and the three plugin lists;
  - Codex's `config.toml`, `qwen38-27b.config.toml`, the empty `AGENTS.md`, `rules/default.rules`, `version.json` and the two migration markers.

  He has no skills of his own outside the synced and bundled ones.

### Gotchas

- **A `found` path from `filepath.WalkDir` never descends a linked directory.** The root itself is resolved with `EvalSymlinks` first, so a configuration directory kept as a link to a dotfiles checkout is still read.
- **A file in a dotfiles setup that is itself a link** is snapshotted as a link, by the rule, so its content is not kept. Worth knowing if Michael ever links `settings.json`.
- **Snapshot names are in UTC** (`20261116T020118Z-start-up`); the listing shows local times.
- **A snapshot outlived its service.** `TestASecondMegaNamesTheFirst` starts a real mega, which now snapshots in the background. After the test it left `snapshots/` folders behind in the temporary directory, written after cleanup had removed it. `Service.Close` never waited for background work. It now stops new snapshots and waits for one under way before letting go, so a snapshot cannot write into a data directory another mega may hold by then. A configuration with nothing on the include lists, as in that test's empty HOME, is no longer snapshotted at all.
