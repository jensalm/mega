### The cause, confirmed

- **The trace.** An instrumented copy, in scratch only, traced each change of `following` with its scroll numbers, and each pin. A probe sent from above 30 times in one session.
- **The probe.** 20 of 30 sends stayed away from the bottom, a higher rate than the suite's, since the probe sends back to back. Every failing trace has the same shape:
  1. `fit` closes the box;
  2. `toLatest` pins the view at the end (scrollTop 7468, height 8168);
  3. 12 ms later the scroll event that pin queued is read with height 8222. The content grew 54px, past the 32px slack, so `following` turns off.
  4. Every later activity only sets "newer", and the dock's resize observer pins nothing (`resize-nopin`).

  That is the card's suspicion exactly.
- **What grew.** The 54px is the in-flight turn's placeholder from 6839018: the `.turn-end.pending` block with its unseen separator, rendered when `turn_active` flips. That changes no activity, and resizes neither the dock nor the column, so nothing re-pins before the queued event is read.
- **The confirmation.** With the placeholder taken out of the instrumented copy, 0 of 30 failed. The placeholder only exposed the fault; the fault is the rule in `latest.ts`, and the fix is there. The placeholder stays.

### How following is decided now

- **There is one `following`, as before.** The scroll listener now also knows what the reader did.
- **It ends** only when a scroll event finds the view moved up since the last one (by more than a pixel), not at the bottom, and the reader started it within the last second. That means a `wheel` or a `touchmove` on the column, or any key whose target is not a text field (`input`, `textarea`, `select`, `[contenteditable]`). It also means a press past the column's client width (the scrollbar), or a middle-button press, held until the pointer is released.
- **Why any key.** The first version counted only scrolling keys, and only where no control or link had the focus. The conversation suite then showed the gap: a view moved to the top with `following` still on is pinned back to the bottom at the next change of the dock. In that run, "Show all" moved away under the click, and no read was made. A reader can move up without a counted gesture, by Tab bringing a control above into view, or by an arrow pressed while a button has the focus. Counting every key outside a text field covers those, and stays safe, since a following view moves up only by the reader: mega's own moves of it go down. The browser's find bar is still a gap after its first second: its own typing reaches no page listener.
- **It begins** whenever a scroll event finds the view at the bottom, within 32px, as before.
- **Nothing else changes it.** A scroll caused by the content growing, a clamp, or mega's own pin leaves `following` as it was. The dock's and `fit`'s rules are unchanged: a view scrolled up is never moved, opening or closing the box keeps the reader's place, and "Newer activity below" appears for activity below.
- **What this means for the checks.** Setting `scrollTop` from a script is not a reader, so it never ends following. Every upward scroll in the two suites now uses the mouse wheel: `wheel` in `panel.mjs`, and `toTop` in `conversation.mjs` for Show earlier, Show all and the streaming step. The panel suite's other scripted scrolls go down to the bottom, which still begins following.

## Batch: the follow rule, simpler (implementation agent)

Michael's review of the fix above: the gesture rule leaves following on for any move up mega does not recognise, and the next activity then pulls the view back to the end. Two such moves are the find bar, and Firefox's overlay scrollbars on Linux, which take no width, so a press on one is not past `clientWidth`. Before the fix any move away from the bottom ended following, so an unrecognised gesture is a regression. He asked for a simpler rule, checked against the code first.

### The rule, checked against the code

**The rule.** Following ends when a scroll event finds the view higher than where it was left last, and not at the bottom. Nothing else ends it. It begins when a scroll finds the view at the bottom. There are no listeners but `scroll`.

**Every place the UI sets the column's position:**
- `latest.ts`: the reset to the top as a conversation opens, `moveToLatest`, the activity pin and the resize-observer pin.
- `InputPanel`'s `fit`: its pin, and its keep-my-place adjustment, which runs only when not following.
- `ConversationView`'s earlier-history anchor, which moves down as rows are added above.

No `scrollIntoView` or `scrollBy`. The only focus moves are to the More menu, which is in the sticky dock, and into modal dialogs, so neither scrolls the column.

**One case where mega moves a following view up.** A pin to the end of a column whose content has just shrunk lands at a lower `scrollTop` than the view had. It happens when:
- the box closes on a send from the bottom, about 79px;
- a docked request leaves.

The event queued by that pin then finds the view higher than the last scroll left it. If the content grows before the event is read, as the in-flight turn's 54px placeholder does, it is also off the bottom, and following would end. As Michael asked, it is handled by marking mega's moves. Every one goes through `place(scroller, top)` in `latest.ts`, which sets the position and records where it ended, in a `WeakMap` keyed by the scrolling column. The scroll handler compares against that record, and updates it with each event it reads.

**The gesture listeners are gone,** with the gesture window, the key filter, and the scrollbar and middle-button detection.
