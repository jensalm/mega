### What held, and what changed

- **What held:** the turn signals, the dialogs (still nothing marking one as an approval), interrupts during a command, the abort blocked by a pending dialog until it is answered, owner-kill recovery, and the two-writer branching with no lock. The local model answered every marker exactly, usually within two seconds a turn.
- **A pending dialog now holds pi open when its input closes.** At 1.1.0 stdin close ended pi in about 40 ms even with a dialog pending. At 1.5.2 it waits; a first SIGTERM waits too; a second ends it at once (exit 143). An abort sent first makes no difference, and a single SIGTERM in R3 took 8 minutes 20 seconds to end it. The 1.5.1 changelog made a started shutdown ignore stdin EOF and a single signal.
- **MCP is built in.** pi starts the user's `mcp.json` servers (Michael's three all connected) and reports them only as the free text of a `notify` answering `/mcp`. There is no structured status.
- **Smaller changes:**
  - a `system` message entry before each user message in the session file;
  - `--session <id>` can prompt `[y/N]` on stdin when the id matches only in another project, so the adapter passes the session file's path;
  - a missing working directory makes `--session` exit with an error.

### The open points, answered

- **Thinking:** model-dependent, reported in `get_state.thinkingLevel`. `qwen3.8-27b` has no reasoning, so its only level is `off`, and the `medium` in Michael's settings is clamped. A conversation's concrete effort is what pi reports, `off`.
- **`@path`:** not attached over RPC, so it does not attach mentions, as Codex does not.
- **The version:** `pi --version` prints `1.5.2`. RPC has none.
- **The conversation's chain:** from the file's last entry back by `parentId`, as pi itself reopens it.
- **Finding pi:** `pi` on `PATH` is a `#!/usr/bin/env node` script, run through `harness.Program` as Codex's `codex.js` is.

## Batch: the pi adapter, step 2, the adapter (implementation agent)

Michael's decisions on step 1's report:
- **Release always works.** With a pi dialog pending, release ends pi's process: its input closed, then signals with bounded waits, then the process group. The dialog is recorded as never answered, and the gated command does not run. mega's own exit takes the same path. The release dialog is to say so before it is confirmed (step 3).
- **Dismiss.** A pi dialog gets a Dismiss control that sends pi's own cancel: the operator's answer, as Escape is in pi's terminal. mega never sends it itself.
- **Unchanged:** an interrupt with a dialog pending still says what it waits on, and the shutdown gate still waits while a request is pending.
- **`models.json` is copied** in a snapshot, as configuration; docs/current is to say a snapshot can hold a secret that lives inside a configuration file.

### What was built

- **`internal/harness/pi`.**
  - `conn.go`: the JSONL process in its own group, split on LF only.
  - `runtime.go`: turns, dialogs, interrupt, close and the exit.
  - `session.go`: session files, the conversation chain, discovery, and the mapping both the live stream and the import use.
  - `trust.go`: the trust notice, read without writing.
  - `pi.go`: check, version, configuration, launch, history, discovery, models, settings.
- **The fake,** `internal/harness/pi/fake/pi`. It writes session files as pi does and holds a pending dialog through stdin EOF and a first SIGTERM, as 1.5.2 does.
- **Identity.** pi's live events carry no session-entry id, but every message's millisecond `timestamp` is written unchanged (checked against the 1.5.2 probe's frames and file). A message's native id is `<role>:<timestamp>`, with `/<index>` for an assistant block.
  - **The prompt.** pi's `prompt` takes no client id, so the service's uuid cannot reach the file. When pi reports the user message it recorded, the adapter records a native event, "user/recorded by pi", under pi's id, and the import skips the prompt.
- **Dialogs are questions,** with no `allow_session`, offering `"dismiss": true`:
  - `select` is a question with its options, and `confirm` one with Yes and No;
  - `input` and `editor` are a one-field form, `value` (editor marked `multiline`, for step 3).
  - **A dialog with a `timeout`** is settled by the adapter as `expired` when it runs out, since pi settles it on its own and sends nothing.
- **Interrupt** sends `abort` without waiting, since pi answers it only once idle, and with a dialog pending records a runtime event, status `waiting`, naming the dialog.
- **Close** closes input, then:
  - after 3 s with a dialog pending (30 s otherwise), a SIGTERM;
  - 3 s later, a second SIGTERM;
  - 3 s later, SIGKILL to the group.

  Pending dialogs resolve `unanswered`, and the exit says mega ended the process.
- **Launch.** A new session is `--session-id <uuid mega mints>`; a resume is `--session <file>`, found by scanning, never the bare id. Each passes `--model provider/id` and `--thinking`, and the start's facts carry no permission mode, plus the trust notice when the checkout's project resources are untrusted.
- **Models and settings** come from a throwaway `pi --mode rpc --no-session --no-mcp`. A model with reasoning lists the levels `set_model` plus `get_available_thinking_levels` give; one without lists none, so its conversation takes no effort.
  - **The writes check:** pi wrote nothing: `settings.json` and `trust.json` keep their October and November 5 times after the e2e run.
- **The service and the config.**
  - **Dismiss:** `harness.DecisionDismiss` is accepted only where the payload offers it.
  - **New names:** `model.OutcomeExpired` and `OutcomeUnanswered`, and `model.StatusWaiting`.
  - **The fill:** its codex-only "lacks an effort" check no longer catches pi.
  - **Config and range:** `pi.binary` in the config, pi in `mega version`, and a tested range of 1.5.2 to 1.5.2.
- **The browser checks' scratch megas** name the fake pi, since node's directory, where the real pi lives, is on their PATH. firstrun now expects three missing harnesses.

### The review

terminus, first pass on the whole pi batch: two blocking findings, both real, both fixed.
- **Identity.** `<role>:<timestamp>` let two tool results of one response, written in the same millisecond, share an id, and the second would be dropped live and on import. The fake hid it by forcing unique timestamps.
  - **The fix:** a tool result is now `toolResult:<toolCallId>` and an assistant message `assistant:<responseId>` where pi gives one; live 1.5.2 messages carry `responseId`, as their files do.
  - **The tests:** a test with two results in one millisecond, and the recorded sessions, still pass. The real round trips were rerun: an import still adds nothing.
- **A cancelled dialog stayed pending.** An extension that passes its dialog pi's abort signal lets an interrupt cancel it, but the adapter kept the dialog pending, and a later answer would be written to a pi no longer reading it.
  - **The fix:** a run that settles aborted or failed now settles any dialog still pending as `aborted`, sending nothing.
  - **The test:** the fake gained a `signal` verb for such a dialog, and a test covers it.
- **The second pass** found two more, both fixed:
  - **The ids were still synthesised.** A message with no response id was still keyed by its role and millisecond. Every message is now identified by its session entry's id: live, a worker goroutine handles pi's records in order and asks `get_entries` after a cursor for the first entry with the message's role, timestamp and call, the cursor moving past each match; on import, the file's ids. The fake gained `get_entries` and a `twins` verb, two replies in one millisecond, and a test keeps both. The real round trips' "import adds nothing" now confirms live ids are pi's entry ids.
  - **Gates allowed outside a gate test.** The conversation check and an adapter test allowed the fake's gate only to go on to other assertions; both now block it, and Allow stays where the approval round trip is the subject.
- **The third pass** found two more blocking and one advisory, all fixed:
  - **The fallback id.** With pi no longer askable (its input closed for a release), a message took an id of the adapter's own, which an import would not recognize. The session file is now read with the same cursor first.
  - **A dialog's timeout ran from when the queue reached it,** not from its arrival, so an expired dialog could stay answerable. Records now carry their arrival time, the timer runs to pi's own deadline, and an answer past it is refused.
  - **`AGENTS.md`,** advisory: it now says pi is built and lists `MEGA_E2E_PI_FIXTURE`.
- **The fourth pass** found one: any substitute identity, however narrow, could differ from the entry id an import uses. A message whose entry cannot be found, from pi or its file, is now not recorded at all; a native note says the next import brings it in, and the substitute ids are gone.
- **The fifth pass** found two:
  - **Output hidden behind the note.** Replacing an unmatched message with a native note hid its output from attention while the turn ended success. Unmatched messages now wait, in order, are looked for again as the run settles or pi exits, and any still unfound is recorded with no identity, shown and counted, and the turn or exit ends in error saying an import may bring it in again.
  - **The rerun probe answered blindly.** It answered dialogs by option text, defaulted to the first option and confirmed everything. `probes/pi/probe.mjs` now answers only dialogs named with `--expect 'TITLE_REGEX=>ANSWER'`, with an answer the dialog offers, and stops unanswered on any other. `rerun.sh` names each scenario's dialog. p1 was rerun against the real pi, and an undeclared `sleep 2` gate stopped the run unanswered.
- **The sixth pass** found R1 and R4 still allowing the gate to reach the abort and the owner kill. They now run ungated commands (`timeout N tail -f /dev/null`, in `scenarios/*-ungated.json`) with no `--expect`; both were rerun against the real pi with no dialog raised. The probe's usage comment names `--expect`.
- **The seventh pass was clean.** `make test` and all seven suites pass after it.
