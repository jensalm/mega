### The question the fix does not ask

The service opens a turn for any user message, and any assistant message, tool call or tool result, that the runtime reports while no turn is open and the adapter has not marked `AfterTurn` (`live.go`, `sink.Event`). The turn then ends only on the adapter's `turn_end`. Nothing bounds it, and an interrupt to a harness with no turn of its own produces nothing.

- **Messages that could do what the echo did.** Anything that reaches the stream as a message outside the harness's own turn bracket, with no end coming:
  - **Claude:** other local commands answered on the stream (any `<local-command-stdout>` without `isReplay`, which the new rule now catches as native); a compaction summary delivered outside a turn; a hook's or a background task's message.
    - Each background job ends in a turn of Claude's own, with a `result`. That one is safe.
  - **Codex:** an item notification arriving after `turn/completed` that the adapter does not mark `AfterTurn`; only finished background commands are marked.
  - **pi:** a message an extension injects outside an agent run, `message_end` with no `agent_start` and `agent_end` around it.
  - **None of these has been seen.** They are where to look.
- **Recommendation, not built:**
  - **Turns begin on an explicit signal.** Each adapter knows its harness's bracket: Claude's `system/init` to `result`, Codex's `turn/started` to `turn/completed`, pi's `agent_start` to `agent_end`. The service would then stop inferring a turn from a message, and a message outside a bracket would be recorded as history and open nothing.
  - **No guessed end.** The page should say how long an open turn has gone with no activity, never end it on a guess, since a real turn can be silent for minutes.
  - **An unanswered interrupt says so.** If an interrupt draws no answer at all within a bound, the turn should be shown as "interrupt not answered", and Release offered.

### What changed

1. **Exit.** After the stop is recorded, `Exited` calls `endTurnLocked`, which counts the turn's output and clears it. The transition also clears `interrupting`.
2. **Resume.** `resumeBoundsLocked` reads two seqs before the import: the last runtime `started`, and the newest event. `newestFinishedOutputLocked` then counts only output after that newest event, or after the start and not of native origin.
3. **Answer.** It reserves the request (`live.answering`), and a second answer meanwhile is `conflict`. After delivery it records the resolution and only then takes the request (`settleLocked`). If the harness or an exit settled it in between, it records nothing more.
   - **What an operator sees without a fault:** the card leaves when the answer is recorded, milliseconds later than before. One requests step read the card count at the instant a Codex denial's reply appeared, and now waits for the card to clear.
4. **Stops.**
   - **Michael's ruling,** asked because the rule as written would have stranded pi's interrupt, which waits on a dialog until it is dismissed: refuse Allow, Allow for the session, and chosen or written answers once an interrupt or a release has begun, with `conflict`, not `not_pending`. Keep accepting Deny and Dismiss. Hold those controls on the page.
   - **The service:** `live.interrupting` is set by `Interrupt` while a turn or a request is outstanding, and cleared at the turn's end, a new turn or an exit. The workspace read carries it as `interrupting`.
   - **The page:** `RequestCard` takes `stopping`, through a context its Allow and Answer buttons read, so Deny and Dismiss never see it. The allow keys answer nothing then.
   - **Codex:** the connection's `call` is split into `begin` (send) and `wait`. `answerAsTurn` builds its parameters first, since `turnStart` takes the lock itself; then it checks the stop counter and sends under `r.mu`, and waits outside it.
5. **Catching up.** `refresh` sets `synced` only when `state.again` is false.
6. **The banner.** It says "Shutting down" only when the stream is connected and the workspace current. Connected but stale, it says the page has reached mega again and is reading the workspace.
7. **Claude's history.** This was not larger than it looked. Every one of the 556 assistant messages in the fixture's 149 sessions, Claude Code 2.1.318 to 2.1.326, has a `stop_reason`.
